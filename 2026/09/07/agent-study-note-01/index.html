一、LLM、Agent、SDK 的关系

角色 本质 职责
LLM 推理引擎，无状态 想：理解语义、决定下一步，不执行代码
Agent 配置单元 = instructions + model + tools + guardrails 定义范围：约束 LLM 用什么指令、能调哪些工具
SDK 运行时框架（Runner.run） 执行：跑 Agent 循环、解析并执行 tool_call、回传结果、管护栏/异常

Search Agent 例子

流程：用户提问 → LLM 决策调 WebSearchTool → SDK 执行搜索并回传结果 → LLM 决策调 save_results → SDK 执行写库 → LLM 生成最终答复。LLM 全程不联网、不碰数据库。

二、管理者模式：子 Agent 为什么算"工具调用"

原理：子 Agent 被包装成管理者的一个工具函数。管理者模型只看到普通工具，输出标准 tool_call；工具函数内部才 Runner.run(sub_agent)，结果以 ToolMessage 回传。

原因：

  1. 复用现有运行时（循环、重试、护栏、日志），无需新增 A2A 协议；
  2. 模型无需理解"多智能体"，提示词更简单；
  3. 子 Agent 异常 = 工具失败，统一重试/转人工；
  4. 路由集中：只有管理者知道全部子 Agent，子 Agent 不做意图判断，拿到任务直接执行。

三、A2A：为什么不用广播 + 延迟与随机性

三模式对比

模式 唤醒 Agent 数 冲突 维护
广播（同时发全部） ≈N，全跑推理 高：多个 Agent 同时认领 新增 Agent 要改所有提示词
管理者 ≈2 无：预先选定唯一执行者 只维护管理者
点对点 A2A ≈1~3 次转交 中：可能循环转交 每个 Agent 知道部分 Peer

不用广播的原因：① token/延迟成倍，而实际只需 1 个干活；② 模糊请求被多 Agent 同时认领，需额外仲裁，甚至并发执行工具产生脏数据；③ 提示词维护爆炸；④ 难调试。广播仅适合投票/评审。

延迟：A2A 是串行转交，理想 1 次转交（2 轮推理）；但跳数无硬上限，可能多跳绕路甚至死循环 → 需设最大转交次数，超限转人工。管理者固定 2 跳，延迟可控。

随机性：广播才有"谁先响应谁抢占"的并发随机；点对点 A2A 一次只转一个，不存在竞争。它的随机性来自每一跳 LLM 路由可能判错（"东西坏了要退款"被错转给报修 Agent，再转回退款 Agent），表现为多绕一跳，而非谁先接收。

四、护栏分类：输入护栏 vs 输出护栏

输入护栏 input_guardrail 输出护栏 output_guardrail
时机 主 Agent 运行前 模型生成后、返回前
对象 外部用户输入 模型输出
谁执行 仅顶层入口 Agent；handoff 子 Agent 不执行 所有 Agent（含子 Agent）
结果 熔断抛异常，主 Agent 完全不跑 阻断丢弃 或 改写清洗

输入护栏：攻击内容不进模型上下文，省 token；安全护栏必须挂入口 Agent，挂子 Agent 会失效。

输出护栏两种措施：

  • 措施2 阻断：丢弃输出换拒绝话术；流式时表现为"输出一半突然被拒"（模型已生成，事后拦截）；
  • 措施3 改写：正则掩码/小模型重写，剔除风险片段后返回。
  • 输出护栏只能兜底，不能替代输入护栏；原则：安全放在 Agent 外部，不靠 prompt 自我保护。
